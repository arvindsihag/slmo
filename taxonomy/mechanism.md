# Mechanism (M)

**Definition.** Why the failure arises — the design or deployment
decision that produced the observed problem.

Mechanisms connect an observable problem to something a practitioner
can act upon.

## Values

| Mechanism | Description |
|---|---|
| Capability mismatch | Tested capability envelope does not cover real operating conditions |
| Expectation mismatch | Robot behaviour does not match what users expect of the assigned role |
| Accessibility / interface barriers | Some users cannot use the system easily or at all |
| Insufficient recovery | The system cannot detect, explain, escalate, or recover from failure |
| Insufficient transparency | Users cannot tell what the robot is doing or why |
| Environmental mismatch | The physical setting invalidates laboratory assumptions |
| Workflow mismatch | The robot adds monitoring, intervention, or hidden work for staff |
| Maintenance burden | Wear, updates, connectivity, or recurring faults accumulate |
| Stakeholder misalignment | Different parties want different things from the deployment |
| Cost / ROI mismatch | Manufacturing, integration, supervision, or scaling costs exceed benefit |
| Inadequate adaptation | The system cannot adjust to changing tasks, users, or context |

## Why mechanism matters

The same outcome can arise from different mechanisms, and the same
mechanism can produce different outcomes. Recording the mechanism
makes the corrective target visible: interface redesign, workflow
reallocation, recovery design, cost review, or scope reduction.

## Examples from the paper

- **Robo-Barista** — accessibility, reliability, retention
- **Henn-na Hotel** — usefulness, expectation mismatch
- **Lindsey** — insufficient autonomous recovery
- **Blue Jay** — cost, manufacturing, integration
